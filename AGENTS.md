# Project Agents.md Guide

This is a [MoonBit](https://docs.moonbitlang.com) project: a **ClickHouse HTTP
driver** (`liuhuo23/clickhouse-driver`). It talks to ClickHouse over its native
HTTP interface (port 8123), parses `TabSeparatedWithNamesAndTypes` responses,
and supports named (`{name: Type}`) and positional (`?`) parameter binding.
Public API: `connect` / `ping` / `execute_query` / `execute` / `insert` /
`cancel` / `close`, with errors raised as `DbError`
(`ServerError` / `ConnectionError`).

You can browse and install extra skills here:
<https://github.com/moonbitlang/skills>

## Project Structure

- Root package (`./`): the driver itself.
  - `clickhouse-driver.mbt` — implementation.
  - `clickhouse-driver_test.mbt` — blackbox tests (external API).
  - `clickhouse-driver_wbtest.mbt` — whitebox tests (internal details).
  - `moon.pkg` lists package dependencies; `pkg.generated.mbti` is generated by
    `moon info` and must not be edited by hand.
- `cmd/main/` — runnable demo CLI (`moon run cmd/main`); depends on the root
  package as `@lib`.
- `integration/` — integration tests against a **real ClickHouse server**.
  They are disabled by default and fail loudly unless `CLICKHOUSE_INTEGRATION=1`
  is set. Server settings come from `CLICKHOUSE_HOST`, `CLICKHOUSE_PORT`,
  `CLICKHOUSE_USER`, `CLICKHOUSE_PASSWORD`, `CLICKHOUSE_DATABASE`.
- `docs/` — project reports (markdown/PDF) describing the driver.
- `scripts/` — doc/report generation scripts.
- `.github/workflows/` — CI: `check.yml` (unit + Docker-backed integration),
  `publish.yml` (tag-triggered publish), `copilot-setup-steps.yml`.
- `.githooks/` — pre-commit hook running `moon check`; enable with
  `git config core.hooksPath .githooks`.

## Coding convention

- MoonBit code is organized in block style, each block is separated by `///|`,
  the order of each block is irrelevant. In some refactorings, you can process
  block by block independently.

- Try to keep deprecated blocks in a file called `deprecated.mbt` in each
  directory.

- Document every public API block with a `///|` doc comment so `moon info` and
  generated docs stay accurate.

## Tooling

- `moon fmt` is used to format your code properly.

- `moon check --target native` type-checks the project (also what the
  pre-commit hook runs).

- `moon ide` provides project navigation helpers like `peek-def`, `outline`, and
  `find-references`. See $moonbit-agent-guide for details.

- `moon info` is used to update the generated interface of the package, each
  package has a generated interface file `.mbti`, it is a brief formal
  description of the package. If nothing in `.mbti` changes, this means your
  change does not bring the visible changes to the external package users, it is
  typically a safe refactoring.

- In the last step, run `moon info && moon fmt` to update the interface and
  format the code. Check the diffs of `.mbti` file to see if the changes are
  expected.

## Testing

- **Unit tests** (no server needed):
  `moon test -p liuhuo23/clickhouse-driver --target native`.
  Plain `moon test` at the repo root also picks up `integration/`, whose tests
  fail without a live server.

- **Integration tests** need a real ClickHouse. CI starts one with Docker:

  ```bash
  docker run -d --rm --name clickhouse -p 8123:8123 \
    -e CLICKHOUSE_USER=default -e CLICKHOUSE_PASSWORD="" \
    -e CLICKHOUSE_DB=default clickhouse/clickhouse-server:24.8

  CLICKHOUSE_INTEGRATION=1 moon test integration/ --target native
  ```

  Or point the `CLICKHOUSE_*` env vars at an existing server.

- MoonBit supports snapshot testing; when changes affect outputs, run
  `moon test --update` to refresh snapshots.

- Prefer `assert_eq` or `assert_true(pattern is Pattern(...))` for results that
  are stable or very unlikely to change. For snapshot tests that record
  structured debugging output, derive `Debug` and use `debug_inspect`, rather
  than deriving `Show` for debugging. For solid, well-defined results (e.g.
  scientific computations), prefer assertion tests. You can use
  `moon coverage analyze > uncovered.log` to see which parts of your code are
  not covered by tests.
